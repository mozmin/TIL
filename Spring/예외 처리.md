# 🚀 현업에서 사용하는 Java/Spring 예외 처리 전략

`try-catch`만으로는 복잡한 애플리케이션의 모든 예외 상황을 처리하기 어려움. 이 문서는 **중앙화된 예외 처리**, **명확한 에러 코드 관리**, **일관된 에러 응답**을 목표로 하는 실무 예외 처리 전략을 설명 함.

## 1. 예외 처리의 핵심 목표

1. **일관된 응답:** 클라이언트(웹/앱)는 어떤 에러가 발생하든 항상 동일한 형식의 JSON 응답을 받아야 함.
2. **명확한 원인:** 에러 메시지만으로 원인을 파악하기 어려움. 고유한 **에러 코드**를 부여하여 원인 파악을 쉽게 함.
3. **중앙화된 관리:** 컨트롤러나 서비스 로직에 `try-catch`를 분산시키지 않고, 한곳에서 모든 예외를 처리.
4. **비즈니스 예외 처리:** "사용자를 찾을 수 없음"과 같은 시스템 장애가 아닌 **비즈니스 로직 상의 예외**를 명확히 구분.

---

## 2. Java 예외: Checked vs Unchecked

- **Checked Exception:** `Exception`을 상속하며, 컴파일러가 `try-catch`나 `throws`를 강제. (예: `IOException`)
- **Unchecked Exception (Runtime Exception):** `RuntimeException`을 상속하며, 컴파일러가 강제하지 않음. (예: `NullPointerException`)

> 💡 [현업 Tip]
전통적으로 Checked Exception을 권장하기도 했으나, 최근 Spring 기반 웹 애플리케이션에서는 비즈니스 예외를 Unchecked Exception으로 만드는 것을 선호하는 추세.
>
>
> **이유:** Checked Exception은 `throws` 구문을 서비스-컨트롤러 계층 전반에 전파시켜 코드를 지저분하게 만듬. 어차피 대부분의 비즈니스 예외는 최종적으로 `@RestControllerAdvice`에서 공통 처리될 것이므로, `RuntimeException`을 상속하여 불필요한 `throws` 선언을 생략.
>

## 3. 핵심 전략: 4가지 구성 요소

이 전략은 4가지 주요 구성 요소를 가짐.

1. `ErrorCode` (Enum)
2. `CustomException` (Custom RuntimeException)
3. `ErrorResponse` (DTO)
4. `GlobalExceptionHandler` (@RestControllerAdvice)

### 1. `ErrorCode` (Enum): 모든 에러 정보의 중앙 관리

`Enum` 값. 단순 메시지뿐만 아니라 **HTTP 상태**, **고유 에러 코드**, **메시지**를 모두 관리.

```java

// /common/exception/ErrorCode.java

import lombok.Getter;
import lombok.RequiredArgsConstructor;
import org.springframework.http.HttpStatus;

@Getter
@RequiredArgsConstructor
public enum ErrorCode {

    // 400 Bad Request
    INVALID_INPUT_VALUE(HttpStatus.BAD_REQUEST, "E400-01", "유효하지 않은 입력값입니다."),
    INVALID_JSON_TYPE(HttpStatus.BAD_REQUEST, "E400-02", "JSON 타입이 유효하지 않습니다."),
    // ...

    // 404 Not Found
    USER_NOT_FOUND(HttpStatus.NOT_FOUND, "E404-01", "해당 사용자를 찾을 수 없습니다."),
    PRODUCT_NOT_FOUND(HttpStatus.NOT_FOUND, "E404-02", "해당 상품을 찾을 수 없습니다."),
    // ...
    
    // 405 Method Not Allowed
    METHOD_NOT_ALLOWED(HttpStatus.METHOD_NOT_ALLOWED, "E405-01", "허용되지 않은 HTTP 메서드입니다."),
    // ...

    // 500 Internal Server Error
    INTERNAL_SERVER_ERROR(HttpStatus.INTERNAL_SERVER_ERROR, "E500-01", "서버 내부 오류가 발생했습니다.");

    private final HttpStatus status;
    private final String code;
    private final String message;
}
```

### 2. `CustomException`: 비즈니스 예외 표현

`ErrorCode`를 담을 수 있는 우리만의 커스텀 `RuntimeException`을 만듭니다.

```java

// /common/exception/BusinessException.java

import lombok.Getter;

/**
* 모든 비즈니스 로직 예외는 이 클래스를 상속.
* 혹은 이 클래스를 직접 사용.
  */
  @Getter
  public class BusinessException extends RuntimeException {

  private final ErrorCode errorCode;

  public BusinessException(ErrorCode errorCode) {
  super(errorCode.getMessage()); // RuntimeException의 message 필드에 저장
  this.errorCode = errorCode;
  }
  }
```

- (선택 사항) `UserNotFoundException`처럼 `BusinessException`을 상속하는 더 구체적인 예외를 만들 수 있음.

```java
  public class UserNotFoundException extends BusinessException {
      public UserNotFoundException() {
          super(ErrorCode.USER_NOT_FOUND);
      }
  }
```

### 3. `ErrorResponse` (DTO): 클라이언트에게 보낼 응답 포맷

예외 발생 시 클라이언트에게 반환할 JSON 응답의 형식을 정의.

```java
// /common/dto/ErrorResponse.java

import lombok.Getter;
import java.time.LocalDateTime;

@Getter
public class ErrorResponse {

    private final LocalDateTime timestamp = LocalDateTime.now();
    private final int status;
    private final String errorCode;
    private final String message;

    public ErrorResponse(ErrorCode errorCode) {
        this.status = errorCode.getStatus().value();
        this.errorCode = errorCode.getCode();
        this.message = errorCode.getMessage();
    }
}
```

### 4. `GlobalExceptionHandler`: 모든 예외의 중앙 처리소

`@RestControllerAdvice` 어노테이션을 사용하여 모든 컨트롤러에서 발생하는 예외를 이 클래스가 가로채서 처리.

```java

// /common/exception/GlobalExceptionHandler.java

import lombok.extern.slf4j.Slf4j;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.MethodArgumentNotValidException;
import org.springframework.web.bind.annotation.ExceptionHandler;
import org.springframework.web.bind.annotation.RestControllerAdvice;

@Slf4j
@RestControllerAdvice // 모든 @RestController에서 발생하는 예외를 처리
public class GlobalExceptionHandler {

    /**
     * 우리가 직접 정의한 BusinessException을 처리.
     */
    @ExceptionHandler(BusinessException.class)
    protected ResponseEntity<ErrorResponse> handleBusinessException(BusinessException e) {
        log.warn("handleBusinessException: {}", e.getMessage());
        
        ErrorCode errorCode = e.getErrorCode();
        ErrorResponse response = new ErrorResponse(errorCode);
        
        return new ResponseEntity<>(response, errorCode.getStatus());
    }

    /**
     * @Valid를 사용한 유효성 검사(Validation) 실패 시 발생하는 예외를 처리.
     */
    @ExceptionHandler(MethodArgumentNotValidException.class)
    protected ResponseEntity<ErrorResponse> handleMethodArgumentNotValidException(MethodArgumentNotValidException e) {
        log.warn("handleMethodArgumentNotValidException: {}", e.getMessage());

        // @Valid 에러는 ErrorCode.INVALID_INPUT_VALUE로 통일
        ErrorCode errorCode = ErrorCode.INVALID_INPUT_VALUE;
        ErrorResponse response = new ErrorResponse(errorCode);
        
        // TODO: e.getBindingResult()를 파싱하여 더 구체적인 메시지를 response에 담을 수 있음

        return new ResponseEntity<>(response, errorCode.getStatus());
    }

    /**
     * 위에서 처리하지 못한 모든 예외를 처리. (최후의 보루)
     */
    @ExceptionHandler(Exception.class)
    protected ResponseEntity<ErrorResponse> handleException(Exception e) {
        log.error("UnhandledException: {}", e.getMessage(), e);

        ErrorCode errorCode = ErrorCode.INTERNAL_SERVER_ERROR;
        ErrorResponse response = new ErrorResponse(errorCode);

        return new ResponseEntity<>(response, errorCode.getStatus());
    }
}

```

## 4. 전체 흐름 (Putting It All Together)

1. **서비스 계층 (Service Layer):** 로직 수행 중 예외 상황 발생 시, `BusinessException`을 `throw`.

```java
   @Service
   @RequiredArgsConstructor
   public class UserService {
   private final UserRepository userRepository;

        public User findUserById(Long userId) {
            // Optional을 사용하여 간결하게 처리
            return userRepository.findById(userId)
                    .orElseThrow(() -> new BusinessException(ErrorCode.USER_NOT_FOUND));
        }
   }
```

2. **컨트롤러 계층 (Controller Layer):** **아무것도 하지 않습니다.** `try-catch`가 필요 없음.

```java
Java

   @RestController
   @RequiredArgsConstructor
   public class UserController {
   private final UserService userService;

        @GetMapping("/users/{id}")
        public ResponseEntity<User> getUser(@PathVariable Long id) {
            // 서비스에서 예외가 발생하면 @RestControllerAdvice가 가로챔
            User user = userService.findUserById(id);
            return ResponseEntity.ok(user);
        }
   }
```

3. **예외 발생:** `UserService`에서 `BusinessException`이 `throw` 됩니다.
4. **예외 처리:** `GlobalExceptionHandler`의 `handleBusinessException` 메서드가 예외를 가로챕니다.
5. **응답 반환:** `ErrorResponse` DTO가 JSON으로 변환되어 클라이언트에게 `HttpStatus.NOT_FOUND` (404) 상태로 응답됩니다.


**[클라이언트가 받는 JSON 응답]**
```json
   {
     "timestamp": "2025-10-21T20:30:00.123456",
     "status": 404,
     "errorCode": "E404-01",
     "message": "해당 사용자를 찾을 수 없습니다."
   }
```
