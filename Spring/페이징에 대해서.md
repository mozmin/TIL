# 실무 페이징(Pagination) 전략 및 최적화

백엔드 개발 시 필연적으로 마주하는 과제, **페이징(Pagination)**. 이는 단순한 페이지 번호 부여를 넘어, 대용량 데이터를 효율적으로 조회하기 위한 핵심 기술.

본 글에서는 Spring Data JPA 환경에서 페이징 처리 시 혼동하기 쉬운 `Page`와 `Pageable` 개념, 그리고 실무 핵심 이슈인 Count 쿼리 분리 및 최적화 전략을 정리.

## 1. 기본 개념: Pageable과 Page, Slice
Spring Data JPA는 페이징을 위한 표준화된 인터페이스를 제공.

**Pageable (요청)**
클라이언트가 서버로 전송하는 페이징 요구사항 인터페이스.
- Page: 페이지 번호 (0부터 시작).
- Size: 한 페이지당 데이터 개수.
- Sort: 정렬 기준.

```java
// 실무: Controller에서 Pageable 객체로 바로 수신
@GetMapping("/members")
public Page<MemberDto> getMembers(Pageable pageable) {
    return memberService.search(pageable);
}
```

**Page<T> (응답 - 게시판형)**
전통적인 "1, 2, 3..." 형태의 페이지네이션에 사용.
- 특징: 전체 데이터 개수(totalCount) 정보 포함.
- 비용: 전체 페이지 수 계산을 위해 반드시 Count 쿼리가 추가 실행.

**Slice<T> (응답 - 무한 스크롤형)**
모바일 환경의 "더 보기" 또는 "무한 스크롤" UI에 적합.
- 특징: 전체 개수(totalCount) 미계산. hasNext() (다음 페이지 존재 여부)만 반환.
- 비용: Count 쿼리 미실행. (요청 Size + 1개를 조회하여 다음 데이터 존재 여부만 판단)

## 2. 핵심 이슈: Count 쿼리와 Select 쿼리 분리 필요성

페이징 구현 시 가장 큰 고민은 **"데이터 조회 쿼리와 카운트 쿼리의 분리 여부"**.

결론부터 말하자면 **"상황에 따라 다르나, 실무에서는 성능 최적화를 위해 분리하는 경우가 다수"**.

**1) 단순한 경우: 분리 불필요**

Spring Data JPA의 기본 메서드(findAll(Pageable))나 단순한 @Query 사용 시에는 프레임워크가 자동으로 Count 쿼리 생성.

```
// Spring이 자동으로 select count(*) from member 실행
Page<Member> findByAge(int age, Pageable pageable);
```

**2) 복잡한 경우: 분리 필수 (성능 이슈 발생)**
데이터 조회 쿼리에 복잡한 JOIN이 포함된 경우, 자동 생성된 Count 쿼리는 성능 저하의 주원인.

**데이터 조회 쿼리 (Content Query):**
```
SELECT m.* FROM member m 
LEFT JOIN team t ON m.team_id = t.id 
WHERE t.name = 'Development'
ORDER BY m.id DESC 
LIMIT 10 OFFSET 0;
```

위 쿼리는 Team 정보를 참조하기 위해 조인 필수.

**자동 생성된 Count 쿼리의 문제점:** 
Spring Data JPA는 원본 쿼리를 기반으로 Count 쿼리 생성.

```
-- 비효율적: 불필요한 조인까지 그대로 수행
SELECT count(m.id) 
FROM member m 
LEFT JOIN team t ON m.team_id = t.id 
WHERE t.name = 'Development';
```

만약 데이터 개수를 세는 데 있어 Team과의 조인이 결과 수에 영향을 주지 않는다면(예: 단순 Left Outer Join), **굳이 무거운 조인을 수행하며 개수를 셀 필요 없음.**

따라서, **Count 쿼리를 별도로 작성하여 불필요한 조인을 제거하는 최적화 필수.**

## 3. 실무 구현 패턴: Count 쿼리 최적화

**방법 1: @Query 사용 시 countQuery 속성 명시**
JPQL 직접 작성 시, countQuery 속성을 통해 가벼운 카운트 쿼리를 별도로 명시 가능.

```
@Query(
    value = "select m from Member m left join fetch m.team t where m.age > :age",
    countQuery = "select count(m) from Member m where m.age > :age" // 조인 제거하여 성능 확보
)
Page<Member> findByAge(@Param("age") int age, Pageable pageable);
```

**방법 2: QueryDSL + PageableExecutionUtils (권장)**

동적 쿼리 처리를 위해 QueryDSL 사용 시, PageableExecutionUtils를 활용하면 효율적 처리 가능.
```java
public Page<MemberDto> searchPageComplex(MemberSearchCondition condition, Pageable pageable) {
    // 1. 컨텐츠 조회 쿼리 (필요한 조인 포함)
    List<MemberDto> content = queryFactory
            .select(new QMemberDto(member.username, member.age, team.name))
            .from(member)
            .leftJoin(member.team, team)
            .where(usernameEq(condition.getUsername()))
            .offset(pageable.getOffset())
            .limit(pageable.getPageSize())
            .fetch();

    // 2. 카운트 쿼리 (최적화: 조인 제거)
    JPAQuery<Long> countQuery = queryFactory
            .select(member.count())
            .from(member)
            // .leftJoin(member.team, team) // 검색 조건에 영향 없으면 제거
            .where(usernameEq(condition.getUsername()));

    // 3. PageableExecutionUtils 사용 (Count 쿼리 실행 제어)
    return PageableExecutionUtils.getPage(content, pageable, countQuery::fetchOne);
}
```

`PageableExecutionUtils.getPage()`의 이점:
다음 상황에서 **Count 쿼리 실행을 생략**하여 성능 최적화.
1. 시작 페이지이면서 컨텐츠 개수가 페이지 사이즈보다 작을 때 (전체 개수 파악 가능).
2. 마지막 페이지일 때 (Offset + 현재 컨텐츠 수 = 전체 개수).
즉, 쿼리는 분리하여 작성하되, 실행 시점은 유틸리티 클래스에 위임하여 불필요한 쿼리 실행 방지.

## 4. 페이징 성능 주의사항: Deep Pagination
페이징 구현 시 가장 주의해야 할 점은 Offset 방식의 성능 한계(Deep Pagination).

**Offset 방식의 문제점**
일반적인 `OFFSET 1,000,000 LIMIT 10` 쿼리의 데이터베이스 동작 방식:

"1,000,000번째부터 읽는다" (X)
"앞에서부터 1,000,010개를 읽은 후, 앞의 1,000,000개를 버리고 10개를 반환한다" (O)

페이지 번호가 뒤로 갈수록(데이터가 많아질수록) 버리는 데이터가 많아져 쿼리 성능 급격히 저하.

**해결책: No-Offset (Cursor Paging)**

"몇 페이지"가 아닌 **"마지막으로 조회한 ID보다 작은 것"**을 조회하는 방식.
```
-- 기존 방식 (데이터 많을수록 느림)
SELECT * FROM member ORDER BY id DESC LIMIT 10 OFFSET 1000000;

-- No-Offset 방식 (인덱스 활용, 빠름)
SELECT * FROM member WHERE id < 1000000 ORDER BY id DESC LIMIT 10;
```

이 방식은 Page(전체 개수 필요)보다는 Slice(더 보기/무한 스크롤) 방식에 적합. 대용량 데이터를 다루는 모바일 리스트 UI에서는 **No-Offset** 방식 도입 적극 고려 필요.

### 요약
1. Page vs Slice: 전체 개수가 필요하면 Page, 무한 스크롤이면 Slice 사용. Slice는 Count 쿼리가 발생하지 않아 더 효율적.

2. Count 쿼리 분리: 단순 쿼리는 유지하되, Join이 포함된 복잡한 쿼리는 성능을 위해 Count 쿼리를 별도로 작성(조인 제거) 필수.

3. 구현 패턴: QueryDSL 사용 시 PageableExecutionUtils를 활용하여 Count 쿼리 실행 여부 자동 최적화 권장.

4. 성능 이슈: 수백만 건 이상의 데이터 조회 시 Offset 페이징은 성능 저하 유발. No-Offset(커서 기반) 페이징으로 전환 고려 필요.
