# 1-2. 생성자에 매개변수가 많다면, 빌더를 고려하라

## 문제 상황

### 생성자
```aiignore
new Account("mozmin", "KRW", 0.02, 0.01, true, 100_000, null, 12);
```
- 매개변수가 많아서 순서가 헷갈림
- 읽기 어렵고 유지보수성 저하

### 자바빈즈(JavaBeans) 패턴
```
Account a = new Account();
a.setOwner("mozmin");
a.setCurrency("KRW");
a.setInterestRate(0.02);
```
- 한 번에 객체가 완성되지 않음 -> 불완전한 상태로 객체 생성 가능
- 불변성 깨짐 / 스레드 안정성 낮음

## 해결책: Builder 패턴

- 필수 매개변수는 생성자에서, 선택 매개변수는 메서드 체이닝으로 설정

```
@Value
public class Range {
    int min;
    int max;

    @Builder // 이 생성자를 기준으로 빌더 생성됨
    private Range(int min, int max) {
        if (min > max) throw new IllegalArgumentException("min > max");
        this.min = min;
        this.max = max;
    }
}
```
- @Value -> final 붙여줌(불변 클래스)
- @Builder -> 체이닝 가능한 빌더 생성
- 검증 로직을 생성자 안에 두면, build() 시점에 검증 시작

## 빌더에 대해서 더 알아보자
### ⚖️ 1. 클래스에 vs 생성자에 @Builder 붙이는 차이
| 구분 |	클래스 위 @Builder |  생성자 위 @Builder | 
|---|---|---|
빌더 인자 |	모든 필드 |	해당 생성자 파라미터만 |
검증 로직|	실행 안 됨 ❌|	실행됨 ✅|
기본값(@Builder.Default)|	동작함|	직접 지정 필요
용도|	DTO, 응답 객체|	도메인, 검증 포함 VO|

🟢 단순 데이터 전달용 → 클래스 위

🟢 검증·도메인 로직 포함 → 생성자 위

### 2. @Builder 속성 정리

Lombok의 @Builder는 단순히 “빌더 만들어줘”가 아니라, 여러 속성을 통해
빌더의 이름, 빌더 메서드 이름, 빌더 클래스 이름 등을 세밀하게 제어할 수 있음.

속성 이름|	기본값|	설명|
|---|--|---|
|builderMethodName	|"builder"	|빌더를 호출할 정적 메서드 이름 지정
|buildMethodName	|"build"	|최종 객체를 생성할 메서드 이름 지정
|builderClassName	|"ClassNameBuilder"	|생성되는 빌더 클래스 이름 지정
|toBuilder	|false	|toBuilder() 메서드 생성 여부 (기존 객체를 기반으로 새로운 빌더 생성)
|access	|AccessLevel.PUBLIC	|빌더 메서드의 접근 제한자 설정
|setterPrefix	|"" (없음)	|빌더 메서드 이름 앞에 접두어 붙이기 (예: setName())

예시)
```aiignore
@Builder(
    builderMethodName = "newBuilder",
    buildMethodName = "create",
    builderClassName = "UserBuilder",
    toBuilder = true
)
public class User {
    private String name;
    private int age;
}

이렇게 설정하면 생성된 빌더 사용 방식은 👇

User u1 = User.newBuilder()     // builderMethodName
              .name("모정민")
              .age(24)
              .create();        // buildMethodName

User u2 = u1.toBuilder()        // toBuilder = true → 기존 값 복사
              .age(25)
              .create();

```
### 3. 필수 생성자, 선택 생성자 설정
```aiignore
public static class Builder {
    private final String owner;     // 필수
    private final String currency;  // 필수
    private Double interestRate = 0.0;
    private Integer termMonths = 0;

    public Builder(String owner, String currency) {
        this.owner = owner;
        this.currency = currency;
    }

    public Builder interestRate(Double v) { this.interestRate = v; return this; }
    public Builder termMonths(Integer v) { this.termMonths = v; return this; }

    public Account build() { return new Account(this); }
}
```
- 생성자쪽에 @Builder를 선언하여 직접 필수 파라미터 지정 및 검증 로직 추가 가능
- 빌더를 완성하기 전에 해당 필수 파라미터가 없다면 build() 불가능

###  4. DTO/도메인 분리
- DTO(단순 데이터 운반, 검증 로직 X) -> 클래스 위에 @Builder
- 도메인(불변 객체, 검증 로직 O) -> 생성자 위에 @Builder, @Value

### 5. @Builder.Default
- 문제점
  - Lombok의 @Builder는 모든 필드를 0, null, false 등으로 초기화
  - 필드 선언 시 기본값을 줘도, Lombok이 그걸 무시
  ```aiignore
    @Builder
    public class User {
    private String name = "Unknown"; // 기본값 주고 싶음
    private int level = 1;
    }
  
    이렇게 설정하면 👇
  
    User u = User.builder().build();
    System.out.println(u.getName()); // ❌ null 나옴
    System.out.println(u.getLevel()); // ❌ 0 나옴
    ```
- 해결책: @Builder.Default 사용
  ```aiignore
    @Builder
    public class User {
    @Builder.Default
    private String name = "Unknown";

    @Builder.Default
    private int level = 1;
    }
    
    이렇게 설정하면 👇
    
    User u = User.builder().build();
    System.out.println(u.getName()); // ✅ "Unknown"
   System.out.println(u.getLevel()); // ✅ 1
  ```
### 6. 빌더 장단점

| 장점            | 단점 |
|---------------|---|
| 가독성 ↑         |코드량 증가 (내부 Builder 클래스)
| 불변성 유지        | 작은 객체엔 과한 설계
| 검증 로직 한 곳에 집중 | 검증 누락 시 늦은 실패 가능
| API 확장성 ↑     | Lombok 기본값 처리 주의(@Builder.Default)

### 7. 정적 팩토리 메소드와의 관계
@Builder를 사용한다는 것은 빌더가 대신 정적 팩토리 메소드를 생성하겠다는 말과 같다.
```java
Member.builder()
```
에서 .builder()가 정적 팩토리 메소드 그 자체이다.

즉, 직접 정적 팩토리 메소드를 쓰기로 결정했다면 둘 중 하나만 쓰거나 아니면 둘 다 같이 쓰거나 해야한다. 클래스 위에 @Builder를 붙이고 클래스 안에 정적 팩토리 메소드를 따로 둘 수 있다.
